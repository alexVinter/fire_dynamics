# Критерии качества и когда делать PR

## Первый модуль и дальше

- **Модуль 1** — это начальное содержимое репозитория. Его просто коммитят и пушат в `main` (или создают репозиторий уже с этим кодом). Отдельный PR для «приёмки» первого модуля не обязателен: репозиторий изначально должен его содержать.
- **Модули 2, 3, …** — добавляются через ветку и **Pull Request**: работа в ветке → коммиты → push ветки → создаёте PR в `main` → вы (как владелец репо) смотрите изменения и нажимаете **Merge**, если всё ок.

## Кто принимает PR

Репозиторием владеете вы — значит, **принимать PR будете вы**: открываете PR на GitHub, смотрите код (и при необходимости проверки из RELEASE_NOTES), затем нажимаете **Merge pull request**. Так пакет считается принятым. Если над кодом работает другой разработчик — он пушит в свою ветку и создаёт PR в ваш репозиторий, принимаете уже вы.

## Когда делать PR

**Один PR = один готовый модуль/пакет** (начиная со второго).

- Модуль 2 готов → ветка с модулем 2 → PR в `main` → вы смотрите и мержите.
- Аналогично для следующих модулей. Внутри модуля можно делать сколько угодно коммитов в ветку; PR создаётся, когда модуль готов к сдаче.

## Как обновляются тесты и критерии по ходу разработки

| Критерий | Обновляется так |
|----------|------------------|
| **Build** | Сборка идёт по всему проекту. Новый код автоматически попадает под `docker compose build` и `npm run build`. |
| **Linter** | Ruff и ESLint проверяют все файлы. Новые файлы подхватываются сами. |
| **Тесты** | При новом модуле/новой логике добавляйте тесты вручную (новый `tests.py` или новые кейсы) в том же или следующем PR. |
| **Release note** | На каждый сдаваемый модуль обновляйте `RELEASE_NOTES.md`: что сделано и как проверить. |
| **PR** | Один PR на один пакет при сдаче (со 2-го модуля). |

Линтеры и сборка подхватывают новый код сами; тесты и RELEASE_NOTES дополняются вручную при разработке каждого следующего модуля.
